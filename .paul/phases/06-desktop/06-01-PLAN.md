<objective>
## Goal
Create `crates/desktop` as a buildable Tauri 2 app that opens `https://vtradingview.com/hub.html` in one
native window, grants the remote origin exactly one permission (`allow-start_sign_in`), refuses every
navigation off that origin, exposes one injected JS function, and has a tray with Show and Quit.

## Purpose
This is the shell the rest of the phase hangs on. Everything else in phase 06 — the deep-link hand-off,
the page-side sign-in branch, the installers — is an addition to this crate. Getting the capability
boundary right *here* is the phase's security gate (SPECIAL-FLOWS phase overrides:
`/configuring-tauri-capabilities`), because a boundary added later is a boundary nobody audits.

The crate is deliberately **not** a root workspace member (D-030). That keeps `cargo test --workspace`
(the phase-05 139-test gate) and the gnu-pinned host toolchain untouched, and it means the desktop crate's
build story is its own, explicit, CI job rather than an accident of a shared `cargo build`.

## Output
- `crates/desktop/` — a Tauri 2 app that builds on MSVC Windows and Linux, with its own `[workspace]`
- `crates/desktop/capabilities/hub.json` — one capability, one permission, remote-scoped
- `crates/desktop/src/nav.rs` — the origin guard, pure and unit-tested
- `crates/desktop/README.md` — how to build it, and why the toolchain is MSVC
- `.gitignore` — `crates/desktop/target/`, `crates/desktop/gen/`
</objective>

```gherkin
Given the guard's unit tests
When is_allowed is applied to https://vtradingview.com/hub.html

When applied to https://vtradingview.com.evil.com/hub.html, https://evil.com/vtradingview.com,
```

Proven both ways: the guard's own test passes, and a **mutation** (swap `host_str() == ...` for

```gherkin
or any other command that is not start_sign_in
```

    Two deliberate choices to keep, each with its reason in a comment in `capabilities/hub.json`:

      A window declared here has no such hooks.

    `capabilities/hub.json` — exactly one permission:

    ```json
    {
      "$schema": "../gen/schemas/remote-schema.json",
      "identifier": "hub",
      "description": "The hosted hub page. One command and nothing else: it may start a sign-in, never touch the filesystem, the shell, the clipboard, the opener, or any event bus.",
      "windows": ["main"],
      "remote": { "urls": ["https://vtradingview.com/*"] },
      "local": false,
      "permissions": ["allow-start_sign_in"]
    }
    ```

    `allow-start_sign_in` is generated by `build.rs`'s `AppManifest::commands(&["start_sign_in"])`
    (`tauri-build-2.5.6/src/acl.rs:100`: "permissions autogenerated in the format of `allow-$command`
    … where $command is the command name in snake_case"). If the build rejects the bare id, the
    generated form is `desktop:allow-start-sign-in` — read the error and use what it names; do not
    invent a third form.

    Do not write a `permissions/` hand-rolled TOML unless the generated id is absent: `build.rs` owns it.

    `local: false` matters: without it the capability also applies to app-local URLs, which is not a
    privilege anyone needs and is one more surface.

    `nav.rs` — the guard, pure and unit-tested. It carries the `validate-origins` rule verbatim: verify
    exact origins for privileged actions; **never** `startsWith`/`includes`/`endsWith` (the guide's
    "Prefix and substring spoofing" case, and the reason `https://vtradingview.com.evil.com` is a real
    attack on a prefix check).

    ```rust
    /// True only for the hosted origin. Equality on scheme AND host, never a prefix:
    /// `https://vtradingview.com.evil.com` starts with the allowed prefix (validate-origins
    /// "Prefix and substring spoofing").
    pub fn is_allowed(url: &url::Url) -> bool {
        url.scheme() == "https" && url.host_str() == Some("vtradingview.com")
            && url.port_or_known_default() == Some(443)
    }
    ```

    Unit tests must cover at least: `https://vtradingview.com/hub.html` true;
    `https://vtradingview.com.evil.com/hub.html`, `https://evil.com/vtradingview.com`,
    `http://vtradingview.com/hub.html`, `https://accounts.google.com/o/oauth2/auth`, a `data:` URL, and
    an empty-host URL all false. AC-2 requires these exact cases.

    `window.rs` — build the window in Rust, wiring both navigation hooks. Measured API
    (`tauri-2.12.7/src/webview/webview_window.rs:266` and `:315`):
    `on_navigation<F: Fn(&Url) -> bool>` and `on_new_window<F: Fn(Url, NewWindowFeatures) -> NewWindowResponse<R>>`.
    `on_navigation` alone does **not** cover `target=_blank`/`window.open`, and `hub.html` frames engine
    pages, so both hooks are wired; a second window is denied and handed to the opener instead.

    On a refused navigation: call `tauri_plugin_opener::open_url(url.as_str(), None::<&str>)` **from
    Rust** (the plugin's JS commands are absent from the capability, so the page cannot reach them), and
    return `false` so the webview stays put.

    Also set an initialization script: `initialization_script(include_str!("init.js"))` — the page
    surface from Task 4's interfaces block. Do not use `withGlobalTauri`.

    `tray.rs` — a tray icon with two menu items, ids `show` and `quit`. `show` calls
    `window.show()` + `set_focus()`; `quit` calls `app.exit(0)`. Closing the window hides it instead of
    exiting (so the tray is the only way out, matching "Show and Quit"); handle
    `WindowEvent::CloseRequested` with `api.prevent_close()` + `window.hide()`.

    `lib.rs` `run()` wires: plugins in the mandated order (`single-instance` first, then `deep-link`,

    instead of starting a second process), then `.setup(|app| { window::build(app.handle(), state)?; tray::build(app.handle())?; Ok(()) })`.
