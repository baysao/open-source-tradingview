<objective>
## Goal
Turn a `vtradingview://auth?code=<code>` deep link into a `vtv:desktop-code` CustomEvent inside the already
loaded page — including when the app was not running (the cold-start path), and including when the window
has not finished loading (the queue path).

## Purpose
This is the half of the sign-in flow that is easiest to get subtly wrong and hardest to see when it is
wrong: the browser completes sign-in, the user returns to the app, and **nothing happens**. Every failure
mode here looks identical from the outside (a waiting overlay that never finishes), so each one gets its
own test rather than being trusted to work.

Three measured facts drive the design:
- `on_open_url` fires only after the app is running; a cold start delivers the URL as **argv**, so the
  handler must also read `deep_link().get_current()`.
- A second launch of the app reaches the running instance only through `single-instance`'s callback
  (registered first), which receives `(app, argv, cwd)`.
- The page's `desktop_key` lives in page memory and dies on any reload, so the code must be delivered
  **without navigating** — the D-029 decision. A fragment navigation would reload the page and orphan the
  key with 45 s left on the code's 60 s life.

## Output
- `crates/desktop/src/deeplink.rs` — validate, queue, deliver
- `crates/desktop/src/state.rs` — the pending queue and the rotation flag
- `crates/desktop/tests/deeplink.rs` — the parser and validator, unit-tested
- `crates/desktop/src/lib.rs` — the wiring: single-instance callback, `on_open_url`, `on_page_load`
</objective>

// src/deeplink.rs — pure, so the parser is testable without a running app.
/// Parses `vtradingview://auth?code=<code>`. Accepts only that scheme, that host, one `code`
/// param, and a base64url body of 16..=128 chars. Anything else is None (never a partial match).
pub fn parse_code(url: &str) -> Option<String>;

/// Delivers the code to the page as a CustomEvent, or queues it when the page is not ready.
/// Needs no capability: `eval` is Rust-side (D-029).
pub fn deliver(app: &tauri::AppHandle, code: &str);

/// Called on PageLoadEvent::Finished: drains the queue and marks the page ready.
pub fn flush(app: &tauri::AppHandle);

**A note on the eval path.** `eval` is WebView2's `ExecuteScriptAsync`, which bypasses the page's CSP and
the ACL. That is the mechanism, and it is why it needs no permission — but it is also why the payload is
built with `serde_json::to_string` and never string-concatenated: the only interpolated value is a code
that `parse_code` has already restricted to `[A-Za-z0-9_-]{16,128}`.

<acceptance_criteria>

## AC-1: The parser accepts exactly the server's shape
```gherkin
Given parse_code
When given "vtradingview://auth?code=abcdefghij_klmnopqrstu"
Then it returns Some("abcdefghij_klmnopqrstu")
When given "vtradingview://auth?code=short", "https://vtradingview.com/auth?code=<valid>",
"vtradingview://other?code=<valid>", "vtradingview://auth?code=<valid>&code=<valid2>",
"vtradingview://auth", "vtradingview://auth?code=<15 chars>", or a code containing "/" or a space
Then every one returns None
```

## AC-2: A deep link delivers the code without navigating
```gherkin
Given the app running with hub.html loaded and signed out
When a vtradingview://auth?code=<code> URL is opened (second launch, i.e. via single-instance)
Then the page receives one 'vtv:desktop-code' CustomEvent whose detail.code is that code
And the window's location is still https://vtradingview.com/hub.html (no reload, no navigation)
And the window does not lose the page's in-memory state
```

## AC-3: A link that arrives before the page is ready is held, not dropped
```gherkin
Given the app running whose window has not finished loading
When a valid deep link arrives
Then delivery happens after the page's load event, exactly once
When two valid deep links arrive before load
Then both are delivered in arrival order, and neither is dropped
```

## AC-4: Cold start works
```gherkin
Given the app is not running
When the OS launches it with vtradingview://auth?code=<code> in argv
Then the code is read from deep_link().get_current() and delivered after the page loads
Then signing in completes without the user clicking anything
```

## AC-5: An invalid link is refused without touching the page
```gherkin
Given the app running
When a deep link with a malformed code, a wrong scheme, or a non-auth host arrives
Then no event is dispatched, the page is unchanged, and one line is logged on target "desktop"
And the app keeps running (no panic, no exit)
```

  <name>Task 1: The parser and its tests</name>
  <depends>none</depends>
  <files>crates/desktop/src/deeplink.rs, crates/desktop/tests/deeplink.rs</files>
  <action>
    `parse_code(url: &str) -> Option<String>` using the `url` crate (already a dependency from 06-01):

    - Scheme must equal `config::DEEP_LINK_SCHEME` exactly (`vtradingview`), host must equal `auth`.
    - Exactly one `code` query parameter; a second one is a refusal (parameter smuggling), so count the
      pairs rather than taking the first.
    - The value must match `[A-Za-z0-9_-]{16,128}` — a deliberate *widening* of the server's 22-char floor
      downward to 16 only for the parser's tolerance, so a future server-generated shorter code does not
      silently break the shell; the authoritative check is still the server's, which refuses anything it
      did not mint. Document that reasoning in a comment so nobody "fixes" the mismatch by tightening the
      client and calling it the guard.
    - Percent-decoding: base64url never needs it, so a value containing `%` is a refusal, not a decode
      attempt. This is the `validate-origins` "unnormalized URLs" lesson applied to the query.

    `tests/deeplink.rs` is a normal Rust integration test over the library (no app needed) and must cover
    every case in AC-1 plus: `vtradingview://auth?code=` (empty), `vtradingview://auth?code=%41%42…`
    (percent-encoded), and a code of 129 chars.

    Do not put the logic in `lib.rs`; the parser must be callable from a test without `tauri::Builder`.
  </action>

    Bare: `cargo +stable-x86_64-pc-windows-msvc test --manifest-path crates/desktop/Cargo.toml --test deeplink; echo exit=$?`

<task type="auto">
  <name>Task 2: The queue and the delivery</name>
  <depends>Task 1</depends>
  <files>crates/desktop/src/deeplink.rs, crates/desktop/src/state.rs</files>
  <action>
    `deliver(app, code)`:
    1. `state.needs_rotation.store(true, Release)` — the next `start_sign_in` mints a fresh key, because
       this code is now bound to the current one.
    2. If `page_ready` is false, push onto `pending` and return. Log at `debug` on target `desktop`.
    3. Else build the payload with `serde_json`:
       ```rust
       let js = format!(
           "window.dispatchEvent(new CustomEvent('vtv:desktop-code', {{detail: {}}}))",
           serde_json::to_string(&serde_json::json!({ "code": code })).unwrap()
       );
       ```
       and `window.eval(js)`. Interpolate **nothing else** — the code is the only variable.
    4. Log the delivery on target `desktop` with the code's length only, never the code
       (the `Refusal` discipline, `crates/hub-core/src/auth/mod.rs:6`).

    `flush(app)`: take the lock, drain `pending` in order, deliver each with `page_ready` already true,
    then release. Set `page_ready = true` **before** draining so a link arriving mid-flush queues rather
    than being lost. AC-3's two-links case is the test for this ordering.

    `page_ready` is set false again on a navigation start (`on_navigation` returning true) so a reload
    cannot deliver into a document that is being torn down.

    Failure handling: if `eval` returns an error, log it and keep the code in `pending` (do not silently
    drop it). A code's 60 s life makes a retry harmless; losing it makes the user repeat the whole
    browser round trip.
  </action>
  <verify>
    Bare: `cargo +stable-x86_64-pc-windows-msvc build --manifest-path crates/desktop/Cargo.toml; echo exit=$?`

    false→true and asserts the queue order and the drain-once property (no `tauri::AppHandle` needed if

    adds, and it exists precisely so AC-3 is testable).
    Mutation: set `page_ready = true` **after** draining, re-run, confirm the two-links case fails.

<task type="auto">
  <name>Task 3: Wire single-instance, on_open_url, cold start, and page load</name>
  <depends>Task 2</depends>
  <files>crates/desktop/src/lib.rs, crates/desktop/src/main.rs</files>
  <action>
    Plugin registration order (fixed by the plugin docs; getting it wrong drops deep links with **no
    error**, which is the failure mode this task exists to prevent):

    ```rust
    tauri::Builder::default()
        .plugin(tauri_plugin_single_instance::init(|app, argv, _cwd| {
            // A second launch: focus the window, then hand any deep link in argv to the same path.
            if let Some(win) = app.get_webview_window("main") { let _ = win.show(); let _ = win.set_focus(); }
            for arg in argv.iter().skip(1) {
                if let Some(code) = deeplink::parse_code(arg) { deeplink::deliver(app, &code); }
            }
        }))
        .plugin(tauri_plugin_deep_link::init())
        .plugin(tauri_plugin_opener::init())
        .invoke_handler(tauri::generate_handler![signin::start_sign_in])
        .setup(|app| {
            let st = DesktopState::new();
            let win = window::build(app.handle(), st.clone())?;
            tray::build(app.handle())?;
            // Ensure the scheme is registered for a dev run; the installed bundle writes the OS
            // registration itself, so this is the dev fallback only.
            #[cfg(any(target_os = "linux", all(debug_assertions, windows)))]
            { let _ = tauri_plugin_deep_link::register("vtradingview"); }
            // Cold start: the URL is in argv, not an event.
            if let Ok(Some(urls)) = app.deep_link().get_current() {
                for u in urls {
                    if let Some(code) = deeplink::parse_code(u.as_str()) { deeplink::deliver(app.handle(), &code); }
                }
            }
            // Warm delivery.
            let h = app.handle().clone();
            app.deep_link().on_open_url(move |event| {
                for u in event.urls() {
                    if let Some(code) = deeplink::parse_code(u.as_str()) { deeplink::deliver(&h, &code); }
                    else { tracing::warn!(target: "desktop", "deep link refused"); }
                }
            });
            // Page readiness drives the flush.
            let h2 = app.handle().clone();
            win.on_page_load(move |_w, payload| {
                if let tauri::webview::PageLoadEvent::Finished = payload.event() { deeplink::flush(&h2); }
            });
            Ok(())
        })
    ```

    The exact `deep_link()` API shape (`get_current`, `on_open_url`, `register`) and the
    `on_page_load` signature must be taken from the installed crate source
    (`~/.cargo/registry/src/*/tauri-plugin-deep-link-2.6.3/src/` and
    `tauri-2.12.7/src/webview/webview_window.rs`) — read them, do not guess: these are the two calls where
    a wrong signature silently compiles into a no-op in some versions.

    `main.rs` stays a one-liner. Do not add a second `invoke_handler` entry.
  </action>
  <verify>
    Bare: `cargo +stable-x86_64-pc-windows-msvc build --manifest-path crates/desktop/Cargo.toml; echo exit=$?` → `exit=0`.
    Then AC-2/AC-3/AC-4 by hand, in this order, recording each:

    2. From a second shell: `cmd //c start "" "vtradingview://auth?code=abcdefghij_klmnopqrstu"`.
       The **already running** app must log a delivery and the page's console must log one CustomEvent.
       The window must not reload (the chart's state survives) — that is AC-2's no-navigation clause.
    3. Kill the app; launch it with the same URL in argv; the code must be delivered after load (AC-4).
    4. Send a malformed link (`vtradingview://auth?code=short`): one `deep link refused` warning, no
       event, app still running (AC-5).
    Note for the runner: the scheme registration comes from the installed bundle, so a bare `cargo run`

## SCOPE LIMITS
- No retry of a failed exchange. The code is single-use and burns on the first attempt
  (`crates/hub-core/src/auth/mod.rs:915`); the user's retry path is "Try again", which mints a new key.
- No persistence of the code or the key to disk. Both are memory-only by design; a restart is a new
  sign-in.
- No tray or window changes beyond what 06-01 built.
- No second command. The page still has exactly one.
