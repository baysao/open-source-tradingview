<objective>
## Goal
Ship `hub/sync.js`: a per-user sync layer that keeps the allow-listed `localStorage` keys identical
across a user's browsers, refuses to overwrite another device's work silently (CUJ 5), and merges a
signed-out visitor's work into their account on first sign-in with a restorable backup (CUJ 3).

## Purpose
This is the phase's user-visible half, and the only part the spec asks for that has real browser
complexity: one writer per tab, a two-way `postMessage` channel, a per-key state machine, and a merge
whose failure mode is destroying somebody's drawings. The server (05-01, 05-02) is deliberately dumb so
that all of that lives in one file that can be driven by a harness.

## Output
- `hub/sync.js` — the sync layer
- `hub/hub.html`, `hub/vela.html`, `hub/lightweight.html`, `hub/klinechart.html` — `sync.js` first

## Facts (measured this session, not from the spec)

**Q5 is answered by measurement, and the spec's own premise is wrong.** The spec says Vela's key names are
built at run time and need a runtime inventory. The bundle does contain such a factory
(`function sZ(e){return{get(t){…localStorage.getItem(e??t)…},set(t,i){…localStorage.setItem(e??t,i)…}}}`
with a `vela-workspace` default), **but `hub/vela.html:148` passes `persist: false`**, so the workspace
key is never written in this app. The only storage seats that exist today are:

| Key | Written by | Page | In the iframe? |
|---|---|---|---|
| `chartHub` | `hub/hub.html:237` | parent | no |
| `chartHubTheme` | `hub/theme.js:36` (`HubSettingsSave`) | every page | both |
| `chartHubIndicators` | `hub/ind_core.js` | parent | no |
| `chartHubFavs` | `hub/ind_core.js`, `hub/ind_dialog.js:62` | parent | no |
| `chartHubScripts` | `hub/ind_core.js`, `hub/pine_editor.js:45` | parent | no |
| `chartHubDraft` | `hub/pine_editor.js:5,6` | parent | no |
| `tradexDrawFavs` | `hub/drawing_favbar.js:7` | iframe (Vela) | yes |
| `tradexFavBar` | `hub/drawing_favbar.js:7` | iframe (Vela) | yes |

`docs/vela-storage-keys.md` therefore records **"no Vela workspace key is written (`persist: false`)"**
plus this table, instead of an inventory of names that cannot be enumerated from source and do not occur
at run time. `vela:` stays in the prefix list as a deliberate placeholder: if a later Vela option turns
persistence on, the key lands inside the allow-list without another plan. This is the difference between
a documented absence and an unverified assumption, and it is why the check is a grep for `persist:` in
`hub/vela.html`, not a browser run.

**`hub/index.html` is a redirect stub.** Ten lines, no chart, a `meta refresh` to `hub.html`, and no
`localStorage` write anywhere. Spec item 41 lists it as an engine page to load `sync.js` into; it is not
an engine page on this branch. `sync.js` is **not** added there — a wrapper installed on a page with no
writers syncs nothing and costs a request on the redirect. Recorded as a plan decision (D-025).

**Load order matters and is currently wrong.** `hub/hub.html:3` loads `theme.js` first and `hub.html:236`
reads `localStorage` at parse time. `sync.js` must be the first script in the document so the
`Storage.prototype` wrapper is in place before any reader or writer runs — the spec says this, and here is
the line that makes it load-bearing.

**The iframe is same-origin** (`hub/hub.html:275` sets `frame.src = "${st.engine}.html?…&embed=1"`, a
relative path), so the parent could reach into `frame.contentWindow.localStorage` directly. It must not:
the wrapper + `postMessage` design is what keeps one writer per tab and what makes a future
cross-origin desktop shell survivable.

**Both sides must validate the origin.** Measured guide `validate-origins`: string equality on
`event.origin` works for a fixed literal, but `Origin.from(event)` + `isSameOrigin()` is the API that
rejects `"null"` (sandboxed) and unnormalised URLs. The pages are same-origin and not sandboxed, so a
literal comparison is sufficient **and** the guide's structured check is the safer default for a
privilege boundary. Use `Origin.from(event)` with a `try/catch` fallback to `Origin.from(event.origin)`
(synthetic `MessageEvent` in tests has no internal origin — the guide documents this exact trap), and
**also** check `event.source` is the window this document expects. `Origin.from` is Baseline; the project
has no explicit browser-support policy, so the fallback path returns "reject" rather than degrading to a
string compare.

**No dependency, no framework, no bundler.** `sync.js` is a plain script that attaches
`window.VtvSync`. It must work when loaded before anything else and must not throw when signed out or
when `/auth/me` is unavailable.

## The client contract this plan implements
From 05-02, verbatim: `GET /api/me/state` → `{"keys":[{key,version,updated_at}]}`;
`GET/PUT/DELETE /api/me/state/{key}`; PUT body `{"value":<string>}` with `If-Match: <n>`, `0` meaning
insert; 200 → `{key,version}`; 409 → `{error:"version conflict",version,value}`; 413 `value too large`;
409 `too many keys`; 428 `if-match required`; 400 `bad if-match` / `bad key`; 401 `sign-in required`.

The stored value is the **string** the page wrote (`JSON.stringify` output), passed through byte-for-byte.
`sync.js` never parses or re-serialises a synced value: a round trip through `JSON.parse` +
`JSON.stringify` would reformat every drawing file and produce false conflicts on the next compare.

## Web-platform guides carried into this plan

`validate-origins` (retrieved, 199 lines) — key rules:
> Use `isSameOrigin()` for strict privilege boundaries: Require an exact `(scheme, host, port)` match when
> handling cross-window `postMessage` commands… Both sides must be `Origin` instances: `isSameOrigin(other)`
> only accept[s] an `Origin` object—passing a raw string throws a `TypeError`.
> Real browser `postMessage` events carry an internal origin extracted by `Origin.from(event)`, whereas
> synthetic `new MessageEvent('message', { origin })` events created in unit tests only populate the
> `event.origin` string and throw on `Origin.from(event)`. Falling back to `Origin.from(event.origin)` inside
> a `try...catch` handles both cleanly while still rejecting invalid or `"null"` strings.
> `'null'` string serialized by `event.origin` for opaque origins, causes `Origin.from()` to throw a `TypeError`.
> Reject `data:` URLs for redirects (`origin.opaque === true`)
> …`Document`, `Request`, and `Response` do **not** define origin-extraction steps and throw a `TypeError` if passed directly to `Origin.from()`.

`persistent-toast-notifications` (retrieved, 197 lines) — key rules:
> **MANDATORY:** Use popover="manual" so the notification stays visible until explicitly closed or timed out by a script.
> **DO** make the container a region, with an accessible name… For example: `<div role="region" aria-label="Notifications"></div>`.
> **DO** use `ariaNotify()` to announce the content present in toasts… If actions are available in the toast, append "Actions available".
> **DO** ensure that only the toast's visible text is announced… and not the names of any controls.
> **DON'T** include controls in toast notifications that perform actions not already permanently available outside the toast notifications.
> **DO** provide a non-animated version using the `prefers-reduced-motion` media query
> **DO** ensure that all toast content remains visible, or can be accessed still, when using a viewport sized to 320 by 256 CSS pixels… 1.4.10 Reflow
> **DON'T** surface toasts in scenarios where focus redirection may be used at the same time. The focus redirection may cancel out the toast announcements.

`dialog` (retrieved, 232 lines) — key rules:
> Use the native `<dialog>` element for modal and non-modal dialogs… provides the accessibility semantics, focus handling, top-layer rendering and `Esc` handling that custom overlays have to rebuild by hand.
> **DON'T** add `role="dialog"`, `aria-modal`, a focus trap, `inert` toggling or an `Esc` handler.
> **DON'T** open it with `show()` or the `open` attribute.
> `dialog:modal { overscroll-behavior: contain; }` … `dialog::backdrop { overflow: hidden; overscroll-behavior: contain; }`

**Precedence note (recorded so neither side wins silently):** `persistent-toast-notifications` says
controls in a toast should only ever mirror actions available elsewhere. The sync notice's actions
(Retry, "Load the other device's version", "Keep mine", Restore a backup) have **no** other permanent
home — they are the only way to resolve a conflict. The notice is therefore built as a **persistent
inline `role="alert"` notice under the header**, which is what the D4 mockup
(`02-sync-notices.html`) specifies and what the guide itself recommends for anything needing immediate
attention ("Notifications that require immediate attention should instead use an alternative component…
inline banners, dialogs"). The toast guide's `popover="manual"` mechanics are **not** used. Its
accessibility rules still bind: a named `role="region"` container for the notice stack, `ariaNotify()`
where available, visible text announcing itself, no focus stealing, reduced-motion variant, and reflow at
320 px.

**D-020 precedent** (native `<dialog>` for destructive confirm) needs no new dialog here: the conflict
choice is a notice, not a modal, and the delete-account dialog already exists from 03-03.

  <name>Task 1: sync.js — the wrapper, the allow-list, and the state machine</name>
  <depends>none</depends>
  <files>hub/sync.js</files>
  <guides>validate-origins, persistent-toast-notifications</guides>
  <action>
    One plain script, no module system, attach `window.VtvSync`. Structure it as four small internal
    pieces plus a thin public surface — the public surface stays tiny because nothing else should depend
    on the internals:

    ```
    window.VtvSync = {
      ready,                    // Promise, settles after the first /auth/me
      signedIn,                 // boolean
      version(key),             // number|null, from vtv:ver:<key>
      on(event, fn),            // 'status' | 'conflict' | 'backups' | 'saved'
      restore(backupKey),       // used by the Restore action
      retry()                   // used by the Retry action
    }
    ```

    **Allow-list.** `const EXACT = new Set(["chartHub","chartHubDraft","chartHubFavs",
    "chartHubIndicators","chartHubScripts","chartHubTheme","tradexDrawFavs","tradexFavBar"])` and
    `const PREFIXES = ["vela:"]`. `allowed(k)` is membership or prefix, and it must **exclude** anything
    starting `vtv:` (the version cache) and `backup:` (server-written). No wildcard `tradex*`: R16 named
    two keys, not a namespace.

    **Wrapper.** Install once, before anything else can write: keep the originals, then
    `Storage.prototype.setItem = function(k, v) { original.call(this, k, v); note(k); }` and the same for
    `removeItem`. Call the original **first** so a quota error still throws to the caller exactly as
    before — swallowing it would change page behaviour and hide the failure from the writer. Guard against
    double installation on a page that somehow loads the script twice (`if (Storage.prototype.__vtv) return;`
    plus a non-enumerable flag).

    `note(key)` decides the role: in the parent (`window.parent === window`) it enqueues directly; in an
    iframe it posts `{vtv:1, t:"set"|"del", key, value|undefined}` to `window.parent` with
    `postMessage(msg, location.origin)` — never `"*"`.

    **Versions.** Read and write `vtv:ver:<key>` through the **original** `getItem`/`setItem`, never the
    wrapped ones, or the version wrote itself into the queue.

    **State machine**, per key: `idle → dirty → (2 s debounce) → inflight → idle | conflict | retry`.
    - Debounce is per key, 2 s, as the spec says; a later write replaces the pending value rather than
      queueing a second PUT.
    - Retry schedule `1, 2, 4, 8, 15 s` with ±20 % jitter, six attempts, then `unsynced`: the value stays
      local, the status line reads offline, and the next write or an `online` event resets the count. A
      409 is **not** retried (it is a decision, not a failure) and a 401 stops syncing and parks the queue
      until sign-in state changes.
    - One writer per tab: only the parent ever calls `fetch`. The iframe's only network act is the
      initial `/auth/me` read, which it can skip entirely by asking the parent over the channel — do that,
      and the iframe makes zero requests.
    - `fetch` with `credentials: "same-origin"`, `headers: {"Content-Type":"application/json",
      "If-Match": String(version)}`. `If-Match: 0` is the insert case (05-02's rule).

    **Origin validation on every inbound message** (guide `validate-origins`, rules quoted in context):
    `try { Origin.from(ev).isSameOrigin(TRUSTED) } catch { try { Origin.from(ev.origin).isSameOrigin(TRUSTED) } catch { return false } }`
    and additionally `ev.source === expectedWindow` (iframes: the `#frame` element's `contentWindow`;
    parent: each known iframe's `contentWindow`). Reject opaque origins — `Origin.from` throws on `"null"`
    and the catch returns false, which is the desired outcome. Use exactly this shape, including the
    nested fallback, because the harness delivers synthetic events in at least one test.

    **Never parse or re-serialise a synced value.** It is a string end to end.

    Do not touch `/auth/me` handling: read `window.VtvAuth`'s existing state if `auth.js` exposes it;
    otherwise call `/auth/me` once and re-read it on the events `auth.js` already emits. Check
    `hub/auth.js` first and prefer its state — a second sign-in implementation is a bug.
  </action>

       back up before adopting**, so a crash mid-merge loses nothing — the worst case is an extra backup.
    4. Keys only on the server: write them into `localStorage` through the **original** `setItem` (do not
       re-queue a sync of the value just downloaded — that would echo the server back to itself and
       manufacture a conflict).

       writes the backup's value back as the live value and uploads it with the current version.

    - `409 too many keys` during the merge: skip that key's backup, keep its local value, and name it in
      the notice as not backed up. The account is full; that is a fact to report, not a retry.
    - `413 value too large`: keep the value local, mark that key `unsynced` permanently for this session,
      and say so in the notice (C7's "Too large to sync: <key>, kept in this browser").

    **`hub/index.html` gets nothing** — it is a redirect stub with no writers (Facts). Note it in the
    SUMMARY as a deliberate omission against spec item 41.
