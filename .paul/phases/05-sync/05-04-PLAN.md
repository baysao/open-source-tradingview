<objective>
## Goal
Clear the four `trigger = "phase:05"` debt rows that are agent-owned (`DEBT-030`, `DEBT-031`,
`DEBT-032`, and the status writeback for rows whose checks already pass), so the phase's own UI evidence
is not the vacuous kind and the store stops reporting work that is finished.

## Purpose
One of these is a hard prerequisite, not housekeeping: **`DEBT-030` blocks 05-03's verification.**
05-03 adds a script to `hub.html` and then claims `gate_all.py --pages hub.html --check-receipts`. Those
receipts cannot pass today — `hub.html` fails 6 of the 8 gates and `index.html` has never been gated — so
05-03's exit claim is impossible until this plan lands. It runs first, in wave 1, in parallel with the
server work.

The rest is the discipline the store exists for: a row whose check passes but whose status still says
`open` teaches the next session that the work is pending, and DEBT-032 is a live defect (a redeploy
reverts the AGPL source offer) rather than a backlog idea.

## Output
- `hub/hub.html` brought to tokens and landmarks, gated served
- `.paul/ds-receipts/current/` holding a passing 8/8 receipt set for `hub.html` and `index.html`
- `data/vtv.db` moved aside; `mise run dev` brings up both services
- `ops/deploy.sh` (or the static route) so `hub/SOURCE.txt` survives `git checkout -f`
- `.paul/DEBT.toml`: `status = "done"` on every row whose check passes
- `.paul/DECISIONS.md`: `D-019`, `D-020`, `D-021` transcribed from `STATE.md`
</objective>

## Why `hub.html` first and not "later"
The sequencing is the point of this plan's wave. 05-03 edits `hub.html` (it adds `sync.js` as the first
script) and then must run the gate set over it. Running the gates over a page that already fails 6 of 8
produces a red run that says nothing about 05-03's work, and shipping `sync.js` into an ungated page makes
the phase's UI claim exactly the "vacuous green" that DEBT-016 and L-019 exist to prevent. Bring the page
under the gates first; then a 05-03 gate run is meaningful.
