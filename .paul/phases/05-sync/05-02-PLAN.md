## Facts (measured this session)

- **Axum is 0.8.9** (`Cargo.lock`), whose path parameters are `{key}`, not `:key`. A `:key` route would
  be parsed as a literal path segment and never match.
- **`tests/gate.rs:66` builds a request URL directly from `RouteSpec.path`**
  (`format!("{base}{}", s.path)`) and iterates every hosted non-GET. With a `{key}` template in the

  `origin_rules_over_every_hosted_non_get` fails on the new routes for a reason that has nothing to do
  with the Origin rule. **This plan must fix the enumeration too**, by substituting a sample value for
  each `{...}` segment before building the URL (`s.path.replace("{key}", "sample")`). Keep the fix inside

- `routes/gate.rs:33` `area()` already matches `/api/me/` as a prefix, so all four routes fall in
  `Area::Me` with no gate change. The gate supplies `axum::Extension<Viewer>` to the handler.
- The gate, before any handler runs, on every non-GET in `/api/me/**`: `Origin` must equal
  `cfg.public_origin` (403 `forbidden origin`); a declared body must be `application/json` (415) and
  under 300,000 bytes (413). **These are not this plan's to re-implement or duplicate.**
- `routes/mod.rs` exports `json(status, body)`, `json_ok(body)` and `api_error(status, msg)`; errors are
  `{"error": "<text>"}` with `Cache-Control: no-store`.
- `lib.rs:346` `spawn_background()` already has a hosted-only block that spawns the hourly

  `body_json`, `cookie_header`. Authenticated requests reuse the session cookie from `sign_in`.
- Error string vocabulary already in use: `sign-in required` (401), `not found` (404),
  `forbidden origin` (403), `JSON only` (415), `too large` (413), `service unavailable` (503).

## The wire contract this plan fixes
05-03 codes against exactly this. Any change here after 05-03 starts is a plan defect, not a refinement.

| Call | Request | Success | Failure |
|---|---|---|---|
| `GET /api/me/state` | — | 200 `{"keys":[{"key","version","updated_at"}]}` | 401 `sign-in required` |
| `GET /api/me/state/{key}` | — | 200 `{"key","value","version","updated_at"}` | 401; 404 `not found` |
| `PUT /api/me/state/{key}` | body `{"value":<string>}`, header `If-Match: <n>` | 200 `{"key","version"}` | 409 `{"error":"version conflict","version","value"}`; 413 `value too large`; 409 `too many keys`; 400 `bad key`; 428 `if-match required`; 400 `bad if-match`; 401 |
| `DELETE /api/me/state/{key}` | — | 204 | 401 |

`version` is an integer. `expected == 0` on PUT means "this key must not exist yet" (an insert).
`value` in the 409 body is the server's current value, so the client can offer "use the other device's
version" without a second request (CUJ 5). `GET /api/me/state` deliberately omits values: it is the
merge and status-snapshot call, and shipping every value would make it the largest response in the app.

    - `put`: `Path(key)`, `HeaderMap` for `If-Match`, body `{"value": String}` via `Json<PutBody>`.
      Order, because each step's refusal must be the specific one the client tests against:
      1. viewer must be a member, else 401 `sign-in required`;
      2. key charset check → 400 `bad key` (see the key rule below);
      3. `If-Match` missing → 428 `if-match required`; present but not a trimmed, quote-and-`W/`-stripped
         decimal integer → 400 `bad if-match`;
      4. `auth.state_put(...)` and map the outcome 1:1: `Stored` → 200 `{"key","version"}`,
         `Conflict` → 409 `{"error":"version conflict","version","value"}`, `TooLarge` → 413
         `value too large`, `TooManyKeys` → 409 `too many keys`.
      Note that `TooLarge` and the gate's own 413 both use the phrase `too large`; the handler's string is
      `value too large` precisely so a test can tell which one refused.
    - `delete`: `Path(key)`, `auth.state_delete`, always 204. A missing key is success (05-01's contract).

    A 409 built from `api_error` would lose the `version`/`value` fields, so the conflict case needs
    `json(StatusCode::CONFLICT, &ConflictBody { error, version, value })` — a real struct, not a manual
    `json!`, so the 05-03 client's field names are compile-checked on this side.

    Key rule (write it as a `fn valid_key(&str) -> bool` in this module): 1 to 128 bytes, all of
    `A-Za-z0-9`, or one of `_`, `-`, `.`, `:` — **`:` is required** because `backup:<key>:<date>` keys are
    written through this same path during a merge. Reject anything else, including `/` (it would collide
    with the path segment) and whitespace.

    Then register: `pub mod state;` in `routes/mod.rs` (alphabetical with its siblings), and four entries
    in `table::hosted()`:
    - `spec(Method::GET, "/api/me/state", get(state::list))`
    - `spec(Method::GET, "/api/me/state/{key}", get(state::get_one))`
    - `spec(Method::PUT, "/api/me/state/{key}", put(state::put))`
    - `spec(Method::DELETE, "/api/me/state/{key}", axum::routing::delete(state::delete))`
    Axum 0.8 syntax: `{key}`, not `:key`. `hosted()` only — local mode has no database and must not mount
    these.

    Do not add a gate branch, a CSP entry, or a rate bucket: `/api/me/**` is already inside `Area::Me`
    and already counted in the `Api` bucket by `net.rs::bucket`.

## SCOPE LIMITS
- No batch endpoint. `sync.js` debounces per key, so a batch would save nothing at steady state and would
  add all-or-nothing semantics and a per-item 409 body.
- No server-side merge. The spec puts the merge in JS; a server merge would need an upsert loop the SQL
  discipline forbids, and would move the one interesting algorithm out of the code that can be tested
  from the browser.
- No `ETag` response header and no strong/weak validator negotiation: `If-Match` on an integer version is
  the whole contract, and `If-Match: *` is not supported (version 0 already means "must not exist").
- No total-bytes-per-user quota (Q7 stays open, as in 05-01).
- No `/api/me/state` entry in `docs/` beyond what 05-03 writes; this plan's contract table is the
  reference until then.
