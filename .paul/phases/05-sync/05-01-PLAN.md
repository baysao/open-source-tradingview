<objective>
## Goal
Give the server a versioned per-user key-value store: migration `0002`, statements `S15..S21` in the one
private home, and three `Auth` methods (`state_all`, `state_put`, `state_delete`) that implement the
optimistic-concurrency rule (stale version = conflict) without any route in front of them yet.

## Purpose
Phase 05's whole feature rests on one server invariant: a write carries the version it last saw, and a
stale write is refused with the current value. Getting this layer wrong is not visible later — the client
would silently overwrite another device's layout, which is exactly CUJ 5. Building it before the HTTP
surface keeps the pgsqlite SQL discipline (D-014) in one place and lets the storage be tested without a
browser.

## Facts (measured this session, not from the spec)

- **The spec's 1 MB value is unreachable.** `routes/gate.rs:120-133` refuses any request that declares a
  body over `300_000` bytes with 413 before the handler runs. A value that must survive JSON escaping
  (≤ 2× growth for `"` and control chars) therefore has a practical ceiling well under 300 KB. This plan
  sets `VALUE_MAX = 262_144` (256 KiB) and names the constant for the measured number, not the spec's.
  Recorded as D-024 at approval.
- `db.rs:29` `MIGRATIONS` currently holds exactly one entry (`version: 1, name: "users"`); migration
  bodies are `include_str!("../migrations/000N_*.sql")`.
- `db.rs` applies one transaction per file and records a checksum in `schema_migrations`; `MIGRATIONS` is
  also walked by `db.rs::tests::every_statement_and_migration_is_single_table` through
  `sql_shape_violations`, so a new migration is shape-checked automatically.
- `auth/store.rs:319` asserts `STATEMENTS.len() == 14`. Adding seven statements without moving that number
  fails the suite — the count is the guard, not an incidental.
- `auth/mod.rs:122` `Auth(Arc<Inner>)`; `Inner { settings, public_origin, db, keys, idp, clock, jwks }`
  — `db` is already there and private, so no new plumbing is needed to reach it from an `Auth` method.
- `auth/mod.rs:75` `Member { user: User, admin: bool, session: SessionHash }`; `user.id: Uuid`.
- pgsqlite bug **DEBT-012**: `UPDATE t SET a = $2 WHERE id = $1` silently matches 0 rows. Every statement
  below numbers placeholders in ascending textual order.
- pgsqlite reports `rows_affected == 0` for an UPDATE that changes nothing, so a 0 there is **not** proof
  of a lost race (03-02 recorded this for `S4`/`S8`). The put path re-reads instead of trusting it.
- SQL discipline (D-014) forbids `RETURNING`, joins, subqueries, casts, SQL functions and column
  defaults. `count(*)` is a function: the 256-key cap counts rows in Rust.
- `L-016`: under `tokio::time::start_paused` the clock jumps while a task waits on I/O, so storage tests
  inject values and never open sockets.

## The decisions this plan carries, and where they came from
Two independent design candidates reached the same shape. Points of difference are settled here, written
down so APPLY does not re-litigate them:

1. **Version is an integer column with compare-and-swap**, not a content hash or ETag. A hash costs a read
   plus a full comparison per write to save four bytes, and pgsqlite's `rows_affected` cannot distinguish
   an equal payload from a lost race.
2. **Statements go in `auth/store.rs` as `S15..S21`**, not a new `state.rs` module. `user_state` is
   account data owned by the account module, and the "one private home plus a `STATEMENTS` shape test"
   rule is the thing that keeps the SQL discipline auditable. A second statement home would be a second
   thing to remember.
3. **The cap is corrective, not preventive**: insert, then count, then delete the row just written if the
   user is over 256. A count-before-insert is two statements and still racy; a lock or a counter column is
   more machinery than a wrong number that self-heals on the next write deserves.
4. **Same-day backups get a time suffix** (`backup:<key>:<YYYY-MM-DD>-<HHMMSS>` UTC) chosen by the
   client from the GET snapshot. No sequence column, no server-side probe loop (R23).

<task type="auto">
  <name>Task 3: Auth::state_all, state_put, state_delete</name>
  <depends>Task 1, Task 2</depends>
  <files>crates/hub-core/src/auth/mod.rs, crates/hub-core/tests/state.rs</files>
  <action>
    Add the domain types and the three methods on `Auth`, next to `resolve` and `delete_account` so the
    module keeps one public surface:

    ```rust
    pub const VALUE_MAX: usize = 262_144;   // 256 KiB: the gate's 300,000-byte body cap is the real ceiling (D-024)
    pub const KEY_MAX: usize = 256;         // keys per user, backups included (spec Q7 leaves the total cap open)

    pub struct StateRow { pub key: String, pub value: String, pub version: i64,
                          pub updated_at: chrono::DateTime<chrono::Utc> }

    pub enum PutOutcome {
        Stored { version: i64 },
        Conflict { version: i64, value: String },
        TooLarge,
        TooManyKeys,
    }
    ```

    - `state_all(&self, member: &Member) -> Result<Vec<StateRow>, AuthError>`: run `S15` over
      `member.user.id`.
    - `state_put(&self, member: &Member, key: &str, value: &str, expected: i64) -> Result<PutOutcome, AuthError>`
      with this exact order, each step a fact the next depends on:
      1. `value.len() > VALUE_MAX` → `Ok(TooLarge)`, before any statement runs.
      2. Read `S16`. There are three cases, and all three must be handled explicitly:
         - absent and `expected != 0` → `Ok(Conflict { version: 0, value: String::new() })` (nothing to
           conflict with; the client's cache is stale). Document that `version: 0` means "the key does
           not exist" in the 409 body.
         - absent and `expected == 0` → `S17`. `rows_affected == 1` ⇒ version 1, continue to step 4.
           `rows_affected == 0` ⇒ a racer inserted first: re-read `S16` and return its
           `Conflict { version, value }`.
         - present and `expected != row.version` → `Ok(Conflict { version, value })` without writing.
         - present and `expected == row.version` → `S18` with `version + 1`. **Do not trust
           `rows_affected`**: pgsqlite reports 0 for an unchanged row. Re-read `S16` and decide from the
           value: version advanced ⇒ `Stored { version }`; unchanged ⇒ `Conflict`.
      3. Never compute the new version in SQL (`SET version = version + 1` is an expression, which D-014
         forbids). Compute `current + 1` in Rust.
      4. Cap enforcement, only on the paths that actually inserted a new key: list `S15`, count in Rust
         (`count(*)` is a function). Over `KEY_MAX` ⇒ undo with `S20` at the version just written, then
         return `Ok(TooManyKeys)`. The undo is bounded to this write's own row, so a concurrent pair
         cannot delete a legitimate row — the loser removes only itself.
    - `state_delete(&self, member: &Member, key: &str) -> Result<(), AuthError>`: `S19`. A missing row is
      success, not 404: `removeItem` is not an error condition and CUJ 4 must not wedge on it.

    Then add `crates/hub-core/tests/state.rs` covering AC-3 through AC-9. Use the `engines!` macro and
    `common::hosted` like `tests/admin.rs`; for the storage tests, build `Auth` over a `TestDb` and a
    `Member` from a signed-in harness, then call the methods directly (no HTTP, no sockets: L-016).
    For AC-7, insert the 256 filler rows with `TestDb::exec` raw SQL rather than calling `state_put` 256
    times — a fixture that goes through the code under test proves nothing about the code under test.

    The filler rows must be valid under the schema: `version = 1`, a real `updated_at`, and keys
    `filler-0000`..`filler-0255` (alphanumeric and hyphen only, so the key rule holds without exception).
