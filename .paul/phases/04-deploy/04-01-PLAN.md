<objective>
## Goal
Everything the production VPS needs except code changes the browser sees: the `ops/` file set
(systemd units, cloudflared config example, nightly `pg_dump` to Cloudflare R2 with a 14-day prune,
a restore drill that never touches production, a deploy script that writes `hub/SOURCE.txt`), the
`tunnel` line in `Procfile` and `scripts/dev.sh`, the Phase 4 load test (`scripts/load_ws.mjs`),
and `"txt"` in the static extension allow-list so `SOURCE.txt` and the licence texts serve.

## Purpose
Phase 04's acceptance starts with "live charts through the tunnel; the host has no inbound ports;
restore drill done". Rehearsing the ops surface now, while today's headers still run, means
04-02's browser-facing changes land on a host that already knows how to deploy, back up and roll
back. The load test is spec item 34 and the NFR's "1,000 concurrent websocket connections,
measured, not assumed".

## Output
`ops/` (8 files), the `tunnel` service in `Procfile` + `scripts/dev.sh`, `scripts/load_ws.mjs`,
one word in `static_files.rs`, `hub/SOURCE.txt`, and a local rehearsal record (drill pass, load
test pass) in the SUMMARY.

## Facts (measured 2026-11-24)
- `Procfile` has two lines (db, hub), each `bash scripts/dev.sh _svc NAME`; gaffa parses plain
  `bash` commands; `scripts/dev.sh` `svc_known` accepts only `db|hub` (line 42) and `svc_port`
  maps db to 55432 and hub to 8770. A `tunnel` line needs both updated.
- `hub-server` always binds 127.0.0.1 (`Config::bind_addr`, both modes) and refuses to start
  missing DATABASE_URL, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, VTV_SECRET_KEY, PUBLIC_ORIGIN
  when AUTH_ENABLED=true (config.rs:140-149). `/api/health` answers feeds health only (D-016:
  no DB readiness check).
- `static_files::resolve` serves top-level files with extensions in `STATIC_EXT` (8 entries,
  no `txt`); any top-level `.html` already serves, so the 04-03 pages need no change here.
- `hub/server.py` and friends stay runnable until 04-03; the contract job in `ci.yml` still
  needs `requirements.txt` unchanged in this plan.
- The spec's Postgres is 17; production runs it as the distro service; pgsqlite remains the dev
  and CI engine (D-011, ci.yml already installs the fork).
- Ports on the VPS: nothing inbound but SSH. cloudflared connects out; hub-server binds
  loopback; Postgres binds loopback.
- The Windows dev machine has no cloudflared; the `tunnel` service must degrade to a clear
  message locally (c2 design, dev.sh `_svc tunnel`).

## AC-1: The ops file set is complete and internally consistent
```gherkin
Given the ops/ directory from this plan
When the README runbook is followed top to bottom on a fresh machine account (dry steps noted)
Then every file it names exists, every env var it requires is in the env-file contract list
  (DATABASE_URL, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, VTV_SECRET_KEY, PUBLIC_ORIGIN,
  ADMIN_EMAILS, R2_BACKUP_REMOTE, R2_BACKUP_BUCKET), and no file contains a real secret
And vtv.service runs the release binary as user vtv with NoNewPrivileges=true,
  ProtectSystem=strict, ReadWritePaths limited to the hub log and cache dirs, PrivateTmp=true,
  RestrictAddressFamilies="AF_INET AF_INET6 AF_UNIX", empty CapabilityBoundingSet,
  Restart=always, and EnvironmentFile=/etc/vtv/env
And cloudflared.yml routes the PUBLIC_ORIGIN hostname to http://127.0.0.1:8770 with a 404
  catch-all service, and no other ingress rule
And backup.sh reads DATABASE_URL from the env file, runs pg_dump --format=custom, uploads
  with rclone to the R2 remote, prunes objects older than 14 days, and exits nonzero when
  the dump is zero bytes or any step fails (set -euo pipefail)
```

## AC-2: The restore drill restores, asserts and cleans up without touching production
```gherkin
Given a scratch Postgres database and one completed backup object
When bash ops/restore_drill.sh runs
Then it downloads the newest backup, restores it into the scratch database (never the one
  DATABASE_URL names), asserts the schema_migrations version matches the binary's
  MIGRATIONS set and prints per-table row counts, boots the release hub-server against the
  scratch on a scratch port with AUTH_ENABLED=true, curls /api/health and /auth/me until they
  answer, tears everything down (its own PIDs only), and prints PASS only if every assertion
  held, else FAIL and nonzero
```

## AC-3: The tunnel line runs through the same paths as db and hub
```gherkin
Given Procfile with the tunnel line and scripts/dev.sh knowing the tunnel service
When gaffa (or `bash scripts/dev.sh dev tunnel`) runs on this Windows dev machine without cloudflared
Then the tunnel service prints one clear message naming what is missing and stays idle (no
  crash loop), while `bash scripts/dev.sh _svc hub` and `_svc db` behave exactly as before
And on a machine with cloudflared installed, `_svc tunnel` runs
  `cloudflared tunnel --config ops/cloudflared.yml run vtradingview`
```

## AC-4: The load test states its mix and proves the NFR
```gherkin
Given a local release (or debug) hub-server with AUTH_ENABLED=false and FEED_MAX_SYMBOLS=400
When node scripts/load_ws.mjs runs with its documented arguments
Then it opens 1,000 connections, average 2 subscriptions each, 50 distinct symbols across Deriv,
  Bybit and Binance, 70 percent M1 and 30 percent H1, holds them for the configured duration
  (default 30 minutes), and prints held connections, dropped connections, memory if available,
  and the server's upstream subscription count read from /api/status or /api/health
And the pass line requires zero dropped connections and upstream count stable at 50
And against live upstreams the test may SKIP a source that refuses the runner's IP, and prints
  which sources served; a run where all sources skipped is not a pass
```
