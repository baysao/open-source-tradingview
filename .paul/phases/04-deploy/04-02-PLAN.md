<objective>
## Goal
The browser-facing security surface of the public site, shipped as one diff: a per-page hashed
Content-Security-Policy computed at boot (`CspSet::scan`), four named rate-limit buckets
(Api 20/40, Auth 5/10, Admin 5/10, Ws 10/30 hosted-only) replacing the single bucket, the TTFC
beacon (`POST /api/metrics/ttfc`) with its admin read (`GET /admin/metrics`), and the reserved
default-chart key (deriv frxXAUUSD) that can never be refused at the feed cap.

## Purpose
ROADMAP's Phase 04 gate: "CSP string that keeps the inline scripts, Google Fonts, Vela Workers
and GIS working, and rate-limit values (R19); feed cap counts symbols and reserves the default
chart (C14, N2); TTFC defined once (C16)". These four share one restart and one test pass; the
inline-block edits and their hashes must ship together, or some window serves a page under a
stale policy.

## Output
`routes/metrics.rs` (new), edits to `static_files.rs`, `net.rs`, `lib.rs`, `table.rs`,
`sources/mod.rs`, `feeds/state.rs`, `hub/ttfc.js` (new) and one beacon line per engine page;
green gates including a CSP live check in a real browser; the 03-03 browser check re-run green
under the new CSP (DEBT-015 discharge attempt).
</objective>

## Facts (measured 2026-11-24)
- Router: `app()` layers rate_limit then security_headers (outermost last: security_headers
  wraps everything including the static fallback and the hosted gate). `fallback()` calls
  `static_files::serve(&st.cfg.static_dir, req)`.
- Gate areas: `area("/api/metrics")` is `None` (gate.rs:179 test); `area("/admin/metrics")` is
  `Area::Admin`; `area("/ws")` is `None`. The beacon POST is outside every gate: it guards
  itself with `net::post_guard`.
- Inline scripts: exactly one bare `<script>` block per page in hub/vela/lightweight/klinechart;
  index.html has none. One `<style>` block per page. Zero `style=""` attributes on all four
  (the c2 claim of style attributes was corrected: 0 measured).
- Runtime `<style>` element injection exists (vela.bundle.js 9 sites, lightweight standalone 1),
  so style-src keeps `'unsafe-inline'`. `new Function` in vela.bundle.js (3 sites, the Pine
  compiler) requires script-src `'unsafe-eval'`: named residual risk for SECURITY.md (04-03).
- Vela workers: both `URL.createObjectURL(new Blob(...))` (blob:) and `new Worker(e)` with a
  same-origin URL (self). `worker-src 'self' blob:` covers both.
- GIS: auth.js:220 sets `s.src = "https://accounts.google.com/gsi/client"` (a DOM-inserted
  script, so script-src must name accounts.google.com; `'self'` does not cover it); GIS iframes
  need frame-src accounts.google.com on hub.html only (the only page loading auth.js).
- Google Fonts: theme.js:53 injects `https://fonts.googleapis.com/css2?...`; font files come
  from fonts.gstatic.com.
- `hub.html` line 233: default chart `st = { engine: "vela", key: "XAUUSD", broker: "deriv",
  ticker: "frxXAUUSD", tf: "M1" }`. `Ticker::parse(Source::Deriv, "frxXAUUSD")` passes it
  through unchanged (ticker.rs test line 34).
- `join()` at the cap evicts the longest-idle upstream (`idle_since` min), else
  `Refusal::Capacity`. `Upstream` carries `epoch`, `idle_since`, `series: BTreeMap<Tf, Series>`,
  `Series.viewers`. `UpstreamKey` is `{source, symbol}` (no tf): the N2 fix already landed in
  Phase 01/02; what remains is C14's reserve.
- ws limits today: `Limits.per_ip = 24`, loopback exempt while auth off. C15's 20-per-IP raise
  was already superseded by the shipped 24; this plan does not touch per_ip.
- The limiter covers `/api/`, `/auth/`, `/admin/` prefixes (`is_limited`); `/ws` is unlimited
  today. Local mode contract tests hammer /api/ at up to 25 rapid calls (parity suite): the Api
  bucket 20/s burst 40 must not break them (it did not in 01-03: same values).
- sha2 and base64 are already hub-core dependencies (Cargo.toml lines 30-31).
- CSP directives the pages need (from the measured origins): default-src 'none'; script-src
  'self' 'unsafe-eval' <hashes> (+ accounts.google.com on hub.html); style-src 'self'
  'unsafe-inline' fonts.googleapis.com; font-src fonts.gstatic.com; img-src 'self' data:;
  connect-src 'self' (+ accounts.google.com on hub.html); frame-src accounts.google.com on
  hub.html, 'none' elsewhere; worker-src 'self' blob:; object-src 'none'; base-uri 'none';
  form-action 'none'; frame-ancestors 'none'; upgrade-insecure-requests appended on https
  origins only.
- TTFC definition (C16 resolution, both candidates agree): "time to first live candle: navigation
  start to the first live bar update rendered on a chart engine page". Window = process lifetime;
  `since` (unix ms) in the admin read makes the window visible. The goldfish report's
  `metrics_ttfc_daily` persistence is NOT adopted: it adds the site's only unauthenticated
  Postgres write path for an ego metric; the spec line 374 already blessed in-memory with loss on
  restart as acceptable, and the gate's operative words are "defined once", which `since`
  satisfies. If all-time TTFC is ever wanted, the upgrade is additive (a flushed counters table;
  shapes unchanged).

```gherkin
Given the built server serving hub.html, vela.html, lightweight.html, klinechart.html, index.html

  the console), sign-in works on hub.html (GIS stub and, once available, the real flow), and the
  Vela chart draws with its Pine worker running
And the CSP response header for a page equals CspSet::scan's per-page policy for that path;
  /api/* responses carry the strict default policy; a path with no inline scripts carries the
  default
And a page edited after boot serves under its boot-time policy (fail closed): the drift is
  visible as a blocked script in the browser, not a silent allow
And a mutation that adds a rogue inline <script> to a page makes the browser block it (hash
  mismatch) while the untouched pages still load
```


## AC-3: TTFC is defined once, bounded, and admin-visible
```gherkin
Given a hosted-mode server (test-idp) and a local-mode server
When POST /api/metrics/ttfc receives {"ms": <0..120000>, "engine": "<vela|lightweight|klinechart>"}
Then it answers 204 in both modes (shared() mount), records into a fixed histogram, and a second
  identical POST records again (no dedup; the rate limiter is the flood control)
And ms over 120000 is 400, a non-numeric ms is 400, an unknown engine is 400, a non-JSON body is
  415 (post_guard), a body over 300000 bytes is 413 (post_guard), a cross-origin POST without
  Origin is allowed (curl) and with a bad Origin is 403 (post_guard)
And GET /admin/metrics signed-in as admin returns {"ttfc": {"since": <unix ms of process start>,
  "engines": {"<engine>": {"count", "p50_ms", "p75_ms", "p95_ms"}}}} with percentile math proven
  by a fixed-bucket unit test
And the same GET signed-out or non-admin is 404 (the gate), and the histogram memory is bounded
  (unit test: 10,000 posts grow nothing)
And the page sends at most one beacon per load: hub.html sends none, each engine page sends one

```
