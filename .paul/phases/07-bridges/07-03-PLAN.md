<acceptance_criteria>
## AC-1: Registration lifecycle, owner-scoped
```gherkin
Given a signed-in session
When POST /api/me/mt5 with {label, url, token}
Then the URL is vetted (syntax + guard) and live-tested (/health then /symbols); success stores the
     bridge with the token sealed and the symbols cache, and answers 201 {id, label, url, symbol_count,
     connected}; a vetting or call failure answers 422 with the exact BridgeError cause text (CUJ 7)
When GET /api/me/mt5
Then only the session's own bridges return, and no response field carries the token
When POST /api/me/mt5/:id/test and DELETE /api/me/mt5/:id for another user's id
Then both answer 404, nothing is tested or deleted (G5)
```

## AC-2: Every SSRF case is refused at the route
```gherkin
Given auth on and a signed-in session
When a bridge URL resolves to loopback, 169.254.169.254, any RFC 1918 net, CGNAT, link-local v6, ULA,
     multicast, unspecified, an IPv4-mapped private form, a name whose first answer is public and
     second private (DNS rebinding), or a URL that 302-redirects to a private address
Then registration and every later call refuse with the specific reason, before any connection to the
     refused target is attempted; with auth off, loopback is accepted for the local bridge only (D-033)
```

## AC-3: Bridge candles reach charts
```gherkin
Given a registered bridge owned by the session and a fake bridge serving /bars and /wait
When GET /api/bars?source=mt5&bridge=<id>&symbol=X&tf=H1&limit=100
Then the bridge's rows map field-for-field onto the BarsResponse (unit test names the mapping); a tf
     outside the bridge's TF_SEC answers the unknown-timeframe error; errors carry the exact cause
When a ws client subscribes {"source":"mt5","bridge":"<id>","symbol":"X","tf":"H1"}
Then a poller long-polls /wait for that (bridge, symbol, tf), broadcasts the changed candle to the
     want's subscribers, is shared by that user's open charts, and stops after the last unsubscribe;
     source=mt5 without bridge keeps today's Binance path (the ws parity test stays green)
```

## AC-4: The symbol merge is owner-only and anonymous-identical
```gherkin
Given no session
When GET /api/symbols
Then the response is byte-equal in shape to today's (mt5: "off", arm: "off", G1)
Given a session owning a tested bridge
When GET /api/symbols
Then the bridge's cached symbols append with source "mt5" and the bridge id; a second user's session
     sees neither this user's symbols nor the bridge
```

## AC-5: Logs never carry a bridge token or URL query
```gherkin
Given a registration and a bars call through the bridge
When the logbus ring is read
Then the token string and the bridge URL's query string never appear (the redaction rule's assertion
     greps the ring for both)
```

## AC-6: Mutations at the route layer, red-then-green
```gherkin
Given m1: the owner check dropped from the /api/bars bridge path; m2: loopback accepted with auth on;
      m3: the redirect policy dropped in the client's route use
When each mutation is applied (grepped as landed, L-009) and its suite runs
Then the cross-user suite, the SSRF suite, and the redirect case each fail under their mutation and
      pass after restore (touch restored files, L-013); every judged exit status quoted bare (L-023)
```
