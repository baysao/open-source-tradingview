## Facts
- depends_on 07-03 consumes: the four `/api/me/mt5` route contracts (register, list, test, delete),
  the exact-cause error strings of `BridgeError`, the `/api/symbols` merge (source "mt5", bridge id per
  entry), and the ws subscribe `bridge` field. Without 07-03 unified this plan does not apply.
- **Browser support: the project states no policy line** (none in AGENTS.md, PROJECT.md or the spec).
  This plan therefore avoids Baseline-newly-available surfaces that need fallbacks: results render
  inline (mockup 03's error rows and status lines), not as popover toasts. Suggested policy for the
  owner to adopt later: "Baseline widely available; newly-available only behind a feature detect with a
  working fallback."
- Guide rules carried into Task 1 (retrieved at plan time, 2026-11-26; `persistent-toast-notifications`
  retrieved and rejected: the mockup renders results inline and the guide itself routes important
  information to inline surfaces, so no popover dependency enters):
  - forms (guide id: forms): wrap controls in a `<form>` with an accessible name (aria-labelledby to
    the form's heading); method POST for the mutation; a `name` on every control; semantic input types;
    `type="button"` on helper buttons, never on the primary submit; visible `<label for>` stacked above
    each control; format hints in label or persistent helper text, never placeholder-only; required
    marked visually and with the `required` attribute; non-colour cues for state.
  - validate-input-after-interaction (guide id: validate-input-after-interaction): native constraints
    (`required`, `pattern`) with `:user-invalid` styling so the error state defers until the user
    commits (blur or submit); `:user-valid` optional for success; errors clear themselves on correction;
    error text is visible, starts with an "Error" icon/word, says how to fix; the error id joins
    `aria-describedby` only while the field is invalid (via `data-error`, never referenced in markup);
    timing matrix: clear on `input`, validate on `blur` (if edited), block and route focus on `submit`;
    do not disable submit to block validation; do disable it after a valid submit to stop double-posts.
  - accessible-error-announcement (guide id: accessible-error-announcement): set `aria-invalid="false"`
    until `:user-invalid` matches (Firefox and Safari announce empty required fields from load
    otherwise); a small script syncs ARIA on blur/change/input/invalid; one polite live region on the
    page announces result changes (test result, delete result); after a failed submit move focus to the
    first invalid field.
- Delete confirmation is the inline pattern mockup 03 draws (a two-step inline confirm on the card),
  not a modal; where a modal is ever needed, the D-020 native `<dialog>` rule applies.
- The one-per-view amber rule (DESIGN.md): the add form's submit is the screen's primary action; the
  delete confirm uses the `.btn.danger` style.
- Learnings applied here: L-007 (drive the real served page, read the live log), L-035 (one path
  segment), L-041 (inject axe with addScriptTag), L-043 (re-run surprising counts bare), L-033
  (Playwright launches pass channel:"chrome"), L-037 (authenticated reads via in-page fetch), L-029/
  L-034/L-032/L-040 (driver hygiene: build, port guard, launch pattern, utf-8, self-terminate),
  L-009/L-010 (mutations grepped landed; scripted multi-file edits assert anchors once).
