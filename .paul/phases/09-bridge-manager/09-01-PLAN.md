<objective>
## Goal
A hub-side pairing surface: a signed-in session mints a short-lived single-use code in Settings;
`POST /api/me/mt5/pair` (no session, code-authenticated) registers a bridge through register's
exact existing flow; `POST /api/me/mt5/paired/{id}/revoke` (revoke-secret-authenticated) removes
one bridge. Codes are 10 digits, 10-minute TTL, bound to the minting session's user.
## Purpose
ROADMAP phase 09's pairing half: the VPS manager app (09-02) pairs over HTTPS with only the code
plus the bridge's own URL/token, and unregister works from either side, without weakening D-032's
auth (the gate names this explicitly). Reusing register's flow unchanged is the point: the SSRF
guard, live test order and sealed storage are identical on both paths by construction.
## Output
Migration 0004, pairing store + routes, the Settings "Pair a bridge" control, contract tests in
the 07-03 pattern, and DEBT-044's suite force-added (its trigger is this phase).
</objective>

## AC-1: Migration 0004 and the store
Given the migration runner
When `Db::open` runs against a fresh pgsqlite and a fresh Postgres (CI's db job pattern)
Then `pairing_codes (code_hash bytea PK, session_id_hash bytea NOT NULL REFERENCES sessions(id_hash)
ON DELETE CASCADE, expires_at timestamptz NOT NULL)` exists and `mt5_bridges` gains nullable
`revoke_hash bytea`; the down migration drops both cleanly; D-011/D-014 style holds (no defaults,
no functions, no IF NOT EXISTS, ids and times written by Rust).
## AC-2: Mint is session-gated and bounded
Given a signed-in session
When `POST /api/me/mt5/pairing-code` runs
Then 201 carries a 10-digit code matching `^\d{10}$` (rejection-sampled uniform, not modulo),
stored only as a sha256 hash; a second mint succeeds (multiple live codes allowed) and an older
code stays valid until its own 10-minute expiry; signed-out -> 401 before anything else (the
AC-6 ordering rule from phase 05); codes hash-bound to the minting session's user, so a session
for user B never resolves a code user A minted.
## AC-3: Pair burns the code and reuses register's flow
Given a valid unexpired code, a bridge URL and BRIDGE_TOKEN
When `POST /api/me/mt5/pair` runs without any session cookie
Then the code is burned first (S12/S13 semantics: second use of the same code is 401
`code unknown or expired`, matching the desktop-exchange refusal text family), the resolved
user is the minting session's user, and registration runs register's exact functions — vet_url
auth-on, /health then /symbols live test, seal, insert — so 201 `{id, label, url, symbol_count,
connected, revoke_code}` carries the same fields register's 201 does plus `revoke_code` (43
base64url chars, shown once, stored hashed); a guard-refused URL is 422 with CUJ 7's exact cause
text; wrong token 422 with the bridge's verbatim error.
## AC-4: Revoke removes exactly one bridge
Given a bridge's revoke_code
When `POST /api/me/mt5/paired/{id}/revoke` runs
Then the secret is burned before the delete is attempted, the row is deleted only when the id
matches the burned secret's bridge (foreign id: nothing deleted, 404), response 204; a wrong or
reused revoke_code deletes nothing (G5) and answers 401; a paired-and-revoked bridge disappears
from the owner's GET /api/me/mt5.
## AC-5: The gate's D-032 properties hold on the new surface
Given the full hosted route set
When the 07-03-style contract tests run
Then: both new endpoints sit inside the gate area (401 signed-out before any handler body, the
L-022 pattern); the pair path runs vet_url (a mutation relaxing vet_url's guard makes the pair
test fail — the guard is observable on THIS path, per L-003's placement rule); rate limiting
comes from the existing per-IP bucket (no new bucket, D-032); no code, token or revoke secret
appears in any log line (the logbus redaction set gains the three secrets' shapes).
## AC-6: Settings shows the pairing code
Given a signed-in user on settings.html
When they open the bridge form and press "Pair a bridge" (or equivalent)
Then the minted code renders grouped ("12345 67890") with its expiry, keyboard-complete and
 axe-clean in both themes; the gate receipt set for settings.html stays green served (DEBT-016's
served rule; no file:// measurements).
