<objective>
## Goal
A working second Tauri app (`crates/mt5-manager`) whose window pairs the host's bridge to the
owner's account (URL + token + the Settings code), starts/stops/restarts the bridge and tunnel
scheduled tasks, and shows status: local /health, task state, and the public edge /health.
## Purpose
ROADMAP phase 09's app half. The app is the permanent bridge's operator console (DEBT-043's
discharge mechanism); its webview capabilities stay as locked down as the v0.2 shell's (the phase
gate), and every system call lives in Rust behind a runner seam so the domain tests never touch
schtasks, mise, cloudflared or sockets (L-016's pattern, D-036's test architecture).
## Output
The mt5-manager workspace (tauri-free until built with its own toolchain), CI legs in desktop.yml,
unit tests over recorded runner outputs, and a served-UI look pass on the manager window's HTML.
</objective>

<acceptance_criteria>
## AC-1: The workspace builds under its own lock, root stays tauri-free
Given the root Cargo workspace
When `cargo build/test --workspace` runs at the root
Then crates/mt5-manager is NOT a root member (D-030's second-workspace rule; own Cargo.lock),
the root suite's output names no tauri/webkit/wry crate, and
`cargo test --manifest-path crates/mt5-manager/Cargo.toml` passes without any Tauri system
dependency installed (the domain tests are pure; only the tauri binary needs webkit).
## AC-2: Capabilities as locked down as the v0.2 shell
Given capabilities/manager.json
When the app runs
Then the local window holds exactly the app's own commands (pair, install, control, status,
revoke); no fs, shell, opener, clipboard-write-without-gesture, http or event-bus plugin is
granted to the webview; the config names no remote URLs (D-029's contrast: this app is the
trusted local party, the hub page never loads inside it).
## AC-3: Pair calls the phase-09-01 surface exactly
Given a URL, token and the 10-digit code from Settings
When pair(url, token, code) runs
Then the app POSTs {url, token, label, code} to `<hub>/api/me/mt5/pair` over HTTPS only (an
http:// hub URL is refused before any request), stores {id, revoke_code} in app state on 201,
and surfaces 401/422/502 causes verbatim in the UI (the CUJ 7 exact-cause rule); the stored
revoke_code never appears in a log line.
## AC-4: Control and status go through CommandRunner with recorded-output tests
Given the runner seam
When the domain functions run
Then every schtasks/Run/End/Change, taskkill (Get-CimInstance pattern), mise and cloudflared
invocation is a CommandRunner call; unit tests inject recorded stdout/stderr/exit triples and
assert: start on a running task is a no-op answer, stop+start is restart, a task not found is
the exact error surfaced, /health polling uses the bearer header and a bounded deadline, the
public-edge check hits the tunnel URL (config'd) not 127.0.0.1.
## AC-5: Install is idempotent
Given install_stack() run twice in tests (recorded outputs both passes)
When the second run executes
Then existing scheduled tasks are updated (Set-), not double-registered; bridge.env keeps its
existing BRIDGE_TOKEN (no overwrite); the tunnel create step detects an existing named tunnel
and reuses it; the final /health verify is the same bounded poll. No step prints a secret.
## AC-6: The panel renders clean and keyboard-complete
Given the manager window's ui/
When the render-and-look pass runs (served via tauri dev or a static server for the gates)
Then hub theme variables only, axe 0 violations both themes, every control has a visible focus
state and a real behavior (R-26/R-32), status numbers name their question ("bridge /health:
last answer Xs ago" not a bare dot), and empty/error states name the cause and next action.
</acceptance_criteria>
